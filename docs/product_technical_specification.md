# Техническое задание на развитие Handwriting OCR до версии 1.0

## 1. Статус документа

Документ является действующим продуктовым ТЗ для текущей ветки `0.4.0-dev` и будущего релиза `1.0`.

Он заменяет первоначальный план дальнейшего развития в части будущих требований. Файл [final_technical_specification.md](final_technical_specification.md) сохраняется как описание этапа, на котором проект перешёл от построчного TrOCR к Qwen и распознаванию страниц.

Порядок реализации определён в [product_roadmap.md](product_roadmap.md).

Термины требований:

- **ДОЛЖНО**: обязательное условие версии `1.0`;
- **СЛЕДУЕТ**: требование выполняется, если не выявлено документированное техническое препятствие;
- **МОЖЕТ**: экспериментальная или последующая функция.

## 2. Назначение системы

Handwriting OCR предназначен для локального распознавания русскоязычного рукописного текста на словах, фрагментах, отдельных строках, фотографиях страниц и многостраничных PDF-документах.

Основной сценарий: пользователь загружает документ, получает текст с сохранением порядка строк, проверяет спорные места, редактирует результат и экспортирует итоговый документ.

## 3. Цели версии 1.0

Система ДОЛЖНА:

1. обеспечивать воспроизводимое распознавание страниц моделью, прошедшей закрытый benchmark;
2. сохранять быстрый TrOCR-режим для слов, фрагментов и строк;
3. поддерживать полный локальный workflow документа от импорта до экспорта;
4. работать без передачи пользовательских изображений во внешние OCR API;
5. устанавливаться на Windows без предварительной установки Python и Git;
6. поддерживать контролируемое обновление и откат моделей;
7. собирать исправления только локально и только для явно подтверждённого пользователем обучения;
8. отделять smoke-run, завершённое обучение, оценённого кандидата и production-модель.

## 4. Границы версии 1.0

В обязательный объём входят:

- Windows 10/11 x64;
- локальный FastAPI backend;
- локальный пользовательский интерфейс;
- SQLite или совместимое локальное хранилище;
- TrOCR и Qwen3-VL-2B;
- изображения PNG/JPEG/TIFF/WEBP и PDF;
- экспорт TXT, JSON, DOCX и searchable PDF;
- локальный менеджер моделей;
- тесты, CI, release-сборка и документация.

Не входят в обязательный объём:

- облачная учётная запись и синхронизация;
- мобильное приложение;
- совместное редактирование;
- серверное multi-user развёртывание;
- гарантированная работа Qwen на CPU;
- автоматическое смысловое переписывание распознанного текста;
- Qwen3-VL-8B как production-модель на текущем компьютере.

## 5. Целевые пользователи

1. Пользователь, который оцифровывает школьные тетради, конспекты и личные записи.
2. Исследователь или разработчик, который сравнивает OCR-модели и готовит новые адаптеры.
3. Разметчик, который проверяет строки, координаты и исправленный текст.
4. Пользователь, которому важна локальная обработка документов без облачного OCR.

## 6. Функциональные требования

### FR-001. Импорт

Система ДОЛЖНА:

- принимать один или несколько файлов;
- принимать PDF и поддерживаемые растровые форматы;
- сохранять порядок страниц;
- ограничивать число страниц, размер файла и разрешение изображения настраиваемыми параметрами;
- корректно сообщать о повреждённом или неподдерживаемом файле;
- позволять импорт папки в настольной версии;
- не выполнять OCR автоматически до подтверждения пользователем.

### FR-010. Подготовка изображения

Система ДОЛЖНА поддерживать:

- ориентацию по EXIF;
- поворот на 90, 180 и 270 градусов;
- ручной crop;
- автоматическое выделение листа;
- коррекцию перспективы;
- deskew;
- улучшение контраста и подавление шума;
- удаление тетрадной сетки как отключаемую операцию;
- исходный, обработанный и итоговый preview.

Система СЛЕДУЕТ автоматически оценивать размытие, пересвет, низкий контраст и перспективные искажения и предлагать подходящий preprocessing preset.

### FR-020. Режимы OCR

Система ДОЛЖНА сохранять режимы:

- `fragment`: TrOCR для слова или фрагмента;
- `trocr_lines`: сегментация страницы и TrOCR по строкам;
- `qwen_lines`: Qwen по выделенным строкам;
- `qwen_page`: Qwen по полной странице;
- `qwen_layout`: текст и структурная разметка;
- `compare`: параллельное сравнение моделей;
- `hybrid`: выбор или проверка результата несколькими моделями.

Режим `qwen_layout` до появления отдельного quality gate ДОЛЖЕН иметь статус experimental.

### FR-030. Очередь задач

Для многостраничных документов система ДОЛЖНА:

- создавать устойчивую локальную задачу с уникальным ID;
- показывать статусы queued, running, completed, failed и cancelled;
- показывать прогресс по страницам;
- поддерживать cancel и retry;
- продолжать незавершённую задачу после перезапуска;
- сохранять ошибку конкретной страницы без потери уже готовых результатов;
- не загружать Qwen повторно для каждой страницы одного job;
- ограничивать параллелизм с учётом VRAM.

### FR-040. Редактор документа

Система ДОЛЖНА:

- отображать список и миниатюры страниц;
- позволять менять порядок страниц;
- показывать изображение страницы и распознанный текст рядом;
- отображать overlay найденных строк или блоков;
- связывать выбранную строку изображения с текстом;
- позволять изменять порядок строк;
- поддерживать редактирование, undo/redo, поиск и замену;
- автоматически сохранять черновик;
- хранить исходный OCR отдельно от пользовательской редакции;
- отмечать строки, требующие проверки.

### FR-050. История и review queue

Система ДОЛЖНА:

- хранить исходный файл или его управляемую локальную копию;
- хранить model id, adapter id, revision, режим, preprocessing и время;
- хранить исходный OCR, исправленный текст и оценку пользователя;
- фильтровать историю по дате, модели, режиму и статусу;
- создавать очередь проблемных примеров;
- исключать пример из будущего обучения по команде пользователя;
- экспортировать подтверждённые примеры в версионируемый training manifest.

### FR-060. Экспорт

Система ДОЛЖНА экспортировать:

- TXT с корректным порядком страниц;
- JSON с моделью, режимом, страницами, строками и координатами;
- DOCX с разрывами страниц;
- searchable PDF с текстовым слоем.

Система МОЖЕТ экспортировать ALTO XML и HOCR после появления практического сценария.

### FR-070. Менеджер моделей

Система ДОЛЖНА:

- показывать установленные модели и адаптеры;
- показывать размер, версию, base model и статус;
- загружать модель отдельно от приложения;
- показывать progress и требуемое место на диске;
- проверять SHA-256 или эквивалентную целостность;
- поддерживать удаление неиспользуемой модели;
- поддерживать статусы experimental, candidate и production;
- позволять rollback на предыдущую production-модель;
- не удалять пользовательские документы при обновлении модели.

### FR-080. Диагностика

Система ДОЛЖНА показывать:

- версию приложения;
- Python/runtime profile;
- наличие CUDA, GPU и объём VRAM;
- активную TrOCR-модель;
- base Qwen, adapter, revision и dtype;
- путь к локальному хранилищу;
- свободное место на диске;
- последние ошибки запуска;
- состояние API и очереди.

Токены, секреты и полный пользовательский текст не должны попадать в диагностический экспорт без отдельного подтверждения.

## 7. Модели

### 7.1 Обязательный baseline

TrOCR сохраняется как production-модель для слов, фрагментов и сегментированных строк. Обновление Qwen не должно ухудшать доступность этого режима.

### 7.2 Основная модель страниц

Основным кандидатом является:

```text
Qwen/Qwen3-VL-2B-Instruct
```

Причины выбора:

- модель уже установлена и интегрирована;
- официальный checkpoint имеет Apache-2.0 license;
- размер соответствует целевой RTX 5070 Ti 16 ГБ лучше, чем 8B;
- модель поддерживается текущим Qwen3-VL/Transformers-конвейером;
- LoRA позволяет обучать адаптер без изменения базовых весов.

Репозиторий и точная revision базовой модели ДОЛЖНЫ фиксироваться в manifest каждого run.

### 7.3 Дополнительные эксперименты

Qwen3-VL-4B-Instruct МОЖЕТ быть проверена с QLoRA после стабилизации 2B.

4B-кандидат принимается только если одновременно:

- даёт измеримый прирост качества на gold benchmark;
- помещается в 16 ГБ VRAM в целевом режиме;
- не превышает удвоенную p95 latency модели 2B;
- не усложняет установку до неприемлемого уровня.

Qwen3-VL-8B не является baseline версии `1.0`. Она МОЖЕТ тестироваться позже на более мощном GPU или в доказанном quantized режиме.

## 8. Данные

### DS-001. Реестр датасета

Для каждого датасета ДОЛЖЕН существовать manifest со следующими полями:

- имя и версия;
- источник и revision;
- license;
- дата получения;
- conversion config;
- число документов, страниц и вариантов;
- split strategy;
- SHA-256 файлов разметки;
- число review/invalid примеров;
- commit конвертера.

### DS-010. HWR200

Текущий HWR200 ДОЛЖЕН использовать author-disjoint split. Варианты одной страницы ДОЛЖНЫ принадлежать одному split.

Исходный HWR200 опубликован под Apache-2.0, содержит тексты 200 авторов и три условия съёмки. Производные manifests, model card и публикации результатов ДОЛЖНЫ сохранять ссылку на источник и рекомендуемое авторами цитирование.

Подтверждённые параметры текущей подготовки:

- 3000 документов;
- 11 010 уникальных страниц;
- 33 030 вариантов;
- 26 634 train;
- 3264 val;
- 3132 test;
- 4283 review pages.

Страницы с review-флагом ДОЛЖНЫ быть доступны как отдельная группа. Их влияние ДОЛЖНО проверяться A/B-экспериментом.

### DS-020. Gold benchmark

Gold benchmark ДОЛЖЕН:

- включать минимум 200 вручную проверенных уникальных страниц;
- включать HWR200 и реальные школьные страницы;
- не содержать augmented-копий в основной метрике;
- не использоваться при обучении, подборе prompt или выборе hyperparameters;
- иметь заблокированную версию и checksums;
- хранить причины исключения проблемных страниц.

### DS-030. Пользовательские данные

Пользовательские исправления ДОЛЖНЫ включаться в training export только после явного подтверждения. Экспорт ДОЛЖЕН поддерживать удаление персональных данных и исключение выбранных записей.

## 9. Требования к обучению

### TR-001. Состояния run

Каждый run ДОЛЖЕН иметь отдельный `run_id` и один из статусов:

```text
created
validated
running
interrupted
failed
training_completed
evaluation_completed
candidate_accepted
candidate_rejected
production
```

Статус `training_completed` не должен автоматически означать `candidate_accepted`.

### TR-010. Воспроизводимость

Run manifest ДОЛЖЕН содержать:

- Git commit SHA;
- dataset version и hashes;
- base model id и revision;
- initial adapter;
- все training arguments;
- seed;
- версии Python, PyTorch, Transformers, PEFT и CUDA;
- GPU и VRAM;
- start/end timestamps;
- число обработанных examples и optimizer steps;
- checkpoints и итоговые метрики.

### TR-020. Trainer

Trainer ДОЛЖЕН:

- принимать отдельные train и val datasets;
- оценивать модель во время обучения;
- сохранять лучший checkpoint;
- поддерживать resume с optimizer state;
- иметь early stopping;
- логировать loss, speed и memory;
- корректно завершаться при OOM и повреждённом примере;
- поддерживать BF16 и FP16;
- выполнять evaluation после run;
- сохранять processor и adapter вместе с manifest.

QLoRA МОЖЕТ быть добавлена для 4B и последующих экспериментов. Quantized training не должна внедряться без отдельного сравнения качества с обычной LoRA.

### TR-030. Ступени эксперимента

До полного run обязательны:

1. dataset dry-run;
2. model smoke inference;
3. 100-step performance run;
4. pilot на 512-1000 примерах;
5. 10% run с validation;
6. полный run;
7. test evaluation после фиксации кандидата.

Test split запрещено использовать для выбора checkpoint и hyperparameters.

## 10. Метрики и quality gate

Для каждого кандидата ДОЛЖНЫ считаться:

- CER;
- WER;
- exact-line rate;
- exact-page rate;
- line detection recall/precision для построчных режимов;
- доля пустых и оборванных ответов;
- median и p95 latency;
- peak VRAM;
- доля страниц, отправленных в review;
- устойчивость к трём условиям съёмки.

Модель может получить статус `candidate_accepted`, если:

1. validation и test рассчитаны отдельными этапами;
2. CER на основном gold benchmark улучшен минимум на 10% относительно сильнейшего текущего Qwen page baseline;
3. WER не ухудшен более чем на 2% относительно того же baseline;
4. нет регрессии более 3% CER на школьном поднаборе;
5. empty/truncated responses составляют менее 1% тестовых страниц;
6. модель помещается в 16 ГБ VRAM в заявленном профиле;
7. p95 latency полной страницы не превышает 30 секунд на целевой RTX 5070 Ti для утверждённого input preset;
8. regression-набор пользовательских ошибок не ухудшен;
9. результат воспроизводим повторным evaluation из сохранённого adapter и manifest.

Если исходный baseline уже удовлетворяет абсолютным метрикам лучше заданного порога, итоговое решение всё равно ДОЛЖНО опираться на полный отчёт и анализ ошибок.

## 11. Автоматический router

Router ДОЛЖЕН учитывать:

- выбранный пользователем режим;
- тип документа;
- число и длину строк;
- качество изображения;
- доступный runtime profile;
- согласие TrOCR и Qwen;
- историю ошибок текущей модели.

Router не должен скрытно заменять пользовательский выбор. В auto-режиме UI ДОЛЖЕН показывать фактически применённую модель и причину fallback.

## 12. Хранение данных

Приложение ДОЛЖНО разделять:

- файлы программы;
- модели и cache;
- базу истории;
- пользовательские документы;
- временные изображения;
- training exports;
- логи.

Удаление приложения не должно удалять пользовательские документы без отдельного подтверждения.

Миграции SQLite ДОЛЖНЫ быть версионированы и проверяться тестом обновления с предыдущей схемы.

## 13. API

Текущие recognition endpoints сохраняются для совместимости.

Для фоновых задач ДОЛЖНЫ быть добавлены логические операции:

```text
POST   /api/jobs
GET    /api/jobs/{id}
POST   /api/jobs/{id}/cancel
POST   /api/jobs/{id}/retry
GET    /api/jobs/{id}/pages
PATCH  /api/documents/{id}
POST   /api/documents/{id}/export
GET    /api/models/installed
POST   /api/models/install
DELETE /api/models/{id}
```

Конкретные URL МОГУТ быть скорректированы до реализации, но операции и их поведение обязательны.

## 14. Нефункциональные требования

### NFR-001. Приватность

- Документы обрабатываются локально.
- Телеметрия отключена по умолчанию.
- Сетевой доступ допускается для явной загрузки модели, обновления или открытой пользователем ссылки.
- UI ДОЛЖЕН явно показывать активную сетевую операцию.

### NFR-010. Надёжность

- Ошибка одной страницы не должна уничтожать весь job.
- Черновик документа сохраняется атомарно.
- После аварийного завершения очередь восстанавливается.
- Production adapter проверяется checksum перед загрузкой.
- Должен существовать rollback модели и миграции БД.

### NFR-020. Производительность

- UI не должен блокироваться на время OCR.
- Одна Qwen-модель должна переиспользоваться между страницами job.
- Параллелизм по умолчанию равен одному GPU job.
- Memory leak проверяется прогоном не менее 100 страниц.
- CPU-профиль обязан поддерживать TrOCR; Qwen CPU может быть помечен unsupported.

### NFR-030. Безопасность

- API по умолчанию слушает только `127.0.0.1`.
- Имена загружаемых файлов не используются как доверенные пути.
- PDF и архивы проверяются по размеру и лимитам страниц.
- Секреты не хранятся в репозитории и логах.
- Release содержит checksums.
- Зависимости проверяются автоматизированным dependency scan.

### NFR-040. Сопровождаемость

- Pull request не объединяется при падающих быстрых тестах.
- Critical services должны иметь unit-тесты.
- API contracts должны иметь integration tests.
- GPU и full-dataset tests запускаются отдельным профилем.
- Документация обновляется вместе с изменением пользовательского workflow.

## 15. Установка и выпуск

Приложение ДОЛЖНО иметь:

- bootstrap-installer;
- профили Lite, Full и Developer;
- проверку системных требований;
- отдельную загрузку моделей;
- progress и checksum;
- ярлык запуска;
- корректный uninstall;
- сохранение пользовательских данных при обновлении;
- changelog и номер версии;
- release archive/installer в GitHub Releases.

Модель и адаптер СЛЕДУЕТ публиковать отдельно от исходного кода с model card, base model, license, dataset references, метриками и ограничениями.

## 16. CI/CD

GitHub Actions ДОЛЖЕН выполнять:

1. установку поддерживаемой версии Python;
2. установку лёгких зависимостей;
3. lint/format check;
4. unit и integration tests без загрузки моделей;
5. проверку PowerShell/BAT scripts;
6. сборку release ZIP;
7. загрузку test/build artifacts;
8. dependency/security scan.

GPU-тесты и обучение не должны выполняться на обычном hosted runner. Для них используется локальный или self-hosted профиль с явным запуском.

## 19. Риски

| Риск | Мера |
| --- | --- |
| Ошибочная page-level разметка | Gold subset, review group, reconstruction checks и ручной audit |
| Переобучение на трёх вариантах одной страницы | Group-aware split и sampler, отдельная robustness-оценка |
| OOM на 16 ГБ | 2B baseline, BF16, gradient checkpointing, pilot-run, QLoRA только после теста |
| Улучшение train loss без улучшения CER | Validation во время обучения и обязательный gold benchmark |
| Галлюцинации Qwen | Детерминированный OCR prompt, empty/truncation metrics, hybrid review |
| Слишком тяжёлая установка | Bootstrap и отдельные model profiles |
| Потеря данных при обновлении | Раздельные каталоги, миграции, backup и rollback |
| Языковая коррекция меняет смысл | Исходный OCR хранится отдельно, correction layer отключаемый и показывает diff |
| Ложный статус готовности | Раздельные smoke/training/evaluation/production states |
